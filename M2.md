Maechanism Mapping: Mechanism B

    Which components implement it

        Component: gpio_libgpiod.c
        Role: Requests the PIR (GPIO26) and HC-SR04 ECHO (GPIO24) lines with
        both-edge detection and CLOCK_MONOTONIC timestamps. The kernel handles
        each GPIO interrupt and timestamps the edge; the program blocks in
        gpiod_line_request_wait_edge_events until edges are queued.

        Component: pipeline.c
        Role: The event loop sleeps until an edge or the next deadline. PIR edges go to the motion state machine (pir.c). ECHO edges go to the echo tracker (hcsr04.c), which
        computes pulse width from the kernel's timestamps.

        Component: src/main.c
        Role: --mode=irq is the default; --mode=poll is the baseline it is compared
        against.

        Component: tools/stimulus.c, tools/analyze.c, tools/bench.sh → results/
        Role: The interrupt vs. polling evaluation: latency distributions and CPU
        use.

    Justification: 

    The proximity limit is meaningless if an echo edge is timed more than about 58 µs off, hence kernel-timestamped interrupts.

    iterrupts must happen so there are no gaps where events occur. Motion must start ranging immediately.

Failure Table:

    Component: PIR 
        How it can fail: Dead, unpowered or disconnected 
        How it's detected: Not detected automatically. With the pull-down, a dead
        PIR reads a steady 0, which looks the same as "no motion"
        What the system does: Dead: nothing triggers
        What the log shows: Dead: no motion_* rows at all, and pir_edges=0 in the
        summary. 

    Component: HC-SR04: no echo
        How it can fail: No object in range, a soft or angled target, or late
        reflections from the previous ping.
        How it's detected: The echo tracker times out after 30 ms with no rising
        or falling edge.
        What the system does: Records the failed reading 
        What the log shows: A distance row with empty distance and echo_ok=0
        range_timeouts=N in the summary.

    Component: HC-SR04: bad reading
        How it can fail: Outside 2–400 cm or a missed falling edge.
        How it's detected: Range check on the computed distance.
        What the system does: Stores the reading but marks it invalid; it never
        counts toward a threat.
        What the log shows: A distance row of about 410 cm with echo_ok=0

storage and data:

    What is stored: one CSV row per event
        motion_start and motion_end: from the PIR.
        distance: one HC-SR04 reading, including failed ones (timeouts and out-of-range).
         threat: motion plus a valid echo within --alert-cm, at most one per motion episode.
    
    Rate: it depends on events.
        Nothing moving: 0 rows. Ranging only runs during motion.
        During motion: 1 distance row every --range-ms  plus 2 motion rows and at most 1 threat per episode.
        Size: a row is about 70 bytes
    What happenes when it dies:
        the already written rlogs are preserved in the csv but if the pi dies in the middle of a write, that last line will be cut off 
Constraints and substitutions
	
	When we began drafting up our build for this project we decided that the ideal system would combine visible-light imaging, thermal imaging, and radar to detect wildlife in varying lighting and weather conditions. However, the prototype is constrained by the available sensor budget and project timeline. We therefore selected a Raspberry-pi Camera module and a HC-SR04 PIR motion sensor as well as a distance sensor. The PIR provides an inexpensive motion trigger, while the camera supplies images for AI-based classification. This substitution reduces hardware cost and implementation complexity, but sacrifices thermal detection, as well as nighttime and obstructed-view performance. The prototype will therefore be evaluated within a defined detection area and under specific lighting conditions rather than being claimed to work reliably in all conditions.

eval plan:

    motion trigger latency:
        how we will test:
            Timestamp PIR event and image capture
        target:
            90% or more of captures begin within 1 second of trigger
    Species classification
        how we will test:
            Compare predictions against manually labeled images
        target:
            At least 80% accuracy on held-out test set of supported classes
    False alarms:
        how we will test:
            Record triggers when no target animal is present
        target:
            Fewer than 1 false trigger per hour during a defined test
    Sensor integration
        how we will test:
            Run both sensors through the application in to persistent storage
        target:
            No missing sensor-event records during a 1-hour test
    Resource footprint
        how we will test:
            Record CPU usage and resident memory
        target:
            Establish a baseline and document peak usage under load
    Reliability
        how we will test:
            Run the system continuously and inject sensor-disconnect faults
        target:
            Recover or report each injected fault as specified in the failure-mode table
